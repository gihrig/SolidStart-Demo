# Full-stack SBOM + vulnerability scanning with syft + grype; Snyk abandoned

Issue #18 lists two security boxes — **"Generate SBOM"** and **"Snyk Security Rust —
requires SBOM"** — with a note to "generate an SBOM in CI (or locally) and run
`snyk sbom test` … via the CLI/API". Two research passes
(`backend/docs/research/2026-09-15-rust-sbom-snyk.md`,
`backend/docs/research/2026-09-15-grype-fullstack-scan.md`; every claim cited to a
primary source) found that `snyk sbom test` and `snyk sbom monitor` are
**Enterprise-plan** features (`2026-09-15-rust-sbom-snyk.md:179,227`). This project is on
Snyk's **free** plan, so that path is unavailable. We **abandon Snyk** for this work and
adopt free, open-source tooling that scans the whole mono-repo — Rust back-end and
TypeScript front-end — from one SBOM.

## Decisions

**One project-wide SBOM, generated by `syft`.** A single CycloneDX 1.6 JSON SBOM covers
both subtrees; `syft` catalogs `backend/**/Cargo.lock` and the front-end npm lockfile in
one pass (`2026-09-15-grype-fullstack-scan.md:206-208`). It is committed at the repo root
as `/sbom.cdx.json`. `cargo-sbom` and `cargo-cyclonedx` were rejected because they are
Rust-only and cannot produce a single cross-ecosystem document
(`2026-09-15-rust-sbom-snyk.md:149-160`).

**The SBOM is normalized before commit.** `syft` writes a random `serialNumber` and a
wall-clock `metadata.timestamp` on every run, even with unchanged dependencies (verbatim
from syft source, `2026-09-15-grype-fullstack-scan.md:349-353`); it has no
reproducible-output flag yet (upstream issue #3931 open). We strip those two fields with
`jq 'del(.serialNumber, .metadata.timestamp)'` so the committed SBOM changes only on a
real dependency change. A CI drift guard — regenerate, normalize,
`git diff --exit-code /sbom.cdx.json` — keeps it current, mirroring the existing
`bindings-drift` guard (`.github/workflows/ci.yml`).

**`grype` is the vulnerability gate; `syft` never gates.** `syft` only inventories;
`grype` scans the SBOM (`grype sbom:/sbom.cdx.json`) and fails the build via `--fail-on`.
We set **`grype --fail-on high`** (fails on high + critical; the full npm tree makes a
lower threshold noisy). The severity order is `negligible < low < medium < high <
critical` (`2026-09-15-grype-fullstack-scan.md:122`). **grype returns exit code `2`** —
not `1` — when a finding meets the threshold (verbatim from grype source,
`2026-09-15-grype-fullstack-scan.md:149-160`); CI and the hook must treat `2` as
"vulnerabilities found".

**`cargo-audit` stays as a back-end RustSec supplement.** grype's database is GHSA + NVD +
distro feeds; GHSA already imports RustSec CVEs, but `cargo-audit` reads RustSec directly
and adds `unmaintained` / `unsound` / `notice` / yanked advisories grype does not carry
(`2026-09-15-grype-fullstack-scan.md:268-271`). It runs on the back-end and fails on any
advisory. It is complementary, not redundant.

**The other suggested Rust crates are wired too.** `backend/README.md` ("Consider using
these rust crates to enhance production security") already lists `cargo-deny`,
`cargo-udeps`, `cargo-auditable`, `cargo-audit`, `cargo-geiger`; #18 asks for them. This
decision adopts them alongside the SBOM and the grype gate.

**Where it runs — four surfaces.** (1) A local `cgs` command runs the full chain
(syft → jq → grype → cargo audit). (2) A **pre-push** git hook runs the same local gate —
pre-push, not pre-commit, because a full grype scan loads a large DB and checks the
network on every run (`2026-09-15-grype-fullstack-scan.md:297-302`); the repo already
routes hooks through Vite+ (`core.hooksPath = .vite-hooks/_`). (3) A **PR** CI job
regenerates the SBOM, runs the drift guard, and runs grype + cargo-audit, using Anchore's
official actions (`anchore/sbom-action@v0`, `anchore/scan-action@v7`;
`2026-09-15-grype-fullstack-scan.md:384-408`). (4) A **daily scheduled** CI job re-scans
the committed SBOM to catch new CVEs on unchanged dependencies — the "monitor" half, since
Snyk's monitor is gone.

**Documentation.** The root `README.md` gets a "Security scanning" section (SBOM + overall
posture), referenced from `frontend/README.md` and `backend/README.md`.

**Delivery — multiple tickets.** The SBOM must exist before grype scans it, so the SBOM
ticket blocks the grype ticket. Rough split: T1 SBOM (syft + normalize + commit + drift
guard + local `cgs`) → blocks → T2 grype gate (pre-push + PR + schedule); T3 cargo-audit;
T4 cargo-deny; T5 the remaining crates (`cargo-udeps` needs a nightly toolchain).
`/to-tickets` finalizes the split.

## Considered and rejected

- **Snyk via the SBOM CLI (`snyk sbom test` / `monitor`).** The literal #18 request.
  Rejected: both are Enterprise-only (`2026-09-15-rust-sbom-snyk.md:179,227`) and the
  project is on the free plan.
- **Snyk's SCM/dashboard or VS Code integration for the back-end.** Rejected: the
  developer's VS Code Snyk account is a per-developer IDE tool, not a CI gate, and the
  free plan does not open the SBOM path.
- **`cargo-sbom` / `cargo-cyclonedx` for the SBOM.** Rejected: both are Rust-only, so
  neither can produce the single project-wide (Rust + TypeScript) SBOM chosen here;
  `cargo-cyclonedx` also defaults to CycloneDX 1.3 and writes one file per crate
  (`2026-09-15-rust-sbom-snyk.md:46,51`).
- **grype alone, dropping `cargo-audit`.** Rejected: grype misses RustSec's non-CVE
  signal — `unmaintained` / `unsound` / `notice` / yanked
  (`2026-09-15-grype-fullstack-scan.md:262-271`).
- **A pre-commit grype hook.** Rejected: too heavy per commit (large DB load + network
  check each run). Moved to pre-push.
- **Commit/PR gate with no scheduled scan.** Rejected: a hook only runs on change and
  cannot surface a new CVE on an unchanged dependency; the daily schedule restores
  monitoring.

## Consequences

- **Exit-code handling is load-bearing.** grype exits `2` on findings, `1` on other
  errors, `100` when a DB upgrade is available, `0` when clean
  (`2026-09-15-grype-fullstack-scan.md:166-173`). Any CI/hook logic that assumes `1` for
  "vulns found" is wrong. Without `--fail-on`, grype exits `0` even when it prints
  vulnerabilities.
- **The committed SBOM depends on the `jq` normalize step.** Drop it and the drift guard
  flaps on every run. If upstream issue #3931 adds a reproducible-output flag, the `jq`
  step can be replaced.
- **grype needs network in CI.** It auto-updates its DB each run and fails scans if the DB
  is older than 5 days (`2026-09-15-grype-fullstack-scan.md:297-302`). The pre-push hook
  uses the cached DB (`GRYPE_DB_AUTO_UPDATE=false`) to stay fast and offline.
- **No new third-party account or secret.** Abandoning Snyk removes the `SNYK_TOKEN`
  requirement; all tools are open-source and run in the runner.
- **#18's Snyk box is satisfied by substitution.** The "Snyk Security Rust" intent — scan
  Rust dependencies for vulnerabilities — is met by grype + cargo-audit, not by Snyk.
  Revisit Snyk only on an Enterprise upgrade.
- **Mono-repo-wide.** This is a cross-cutting decision spanning both subtrees
  ([ADR-0010](0010-monorepo-structure.md)); the SBOM and its scan treat the repo as one
  unit.
- **Primary-source record.** The two research files under `backend/docs/research/` hold
  the cited evidence for every tool fact above.
