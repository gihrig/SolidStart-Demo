# Entity identity is `number`, made honest at the type barrel

The generated ts-rs bindings declare entity ids as `bigint`, but every id arrives
via `response.json()` / `JSON.parse`, which yield `number` — so the declared type
never matched the runtime value, and callers papered over the gap with `Number(id)`
coercions across the RPC client, the WebSocket handler, and `createConvMessages`. We
represent identity as plain `number` (matching the JSON wire and the Jedi context,
see [ADR-0002](0002-jedi-mock-data-contract.md)) and make the types honest at the
single import barrel `src/types/backend/index.ts`: a `NumericIds<T>` mapped type
rewrites each binding's `bigint` fields to `number` and re-exports it under the same
name. Because the runtime is already numeric, this is a **type-only** change — there
is no runtime normalizer — and every downstream comparison drops its coercion.

## Considered and rejected

- **Branded `Id` type** (`number & { readonly __entity }`) — rejected: it prevents
  mixing entity ids, but the codebase shows no such bug, and it reintroduces
  per-boundary minting casts (the very ceremony this change removes) plus bespoke
  per-field mapping the generic `bigint → number` rule avoids.
- **ts-rs override / hand-editing the bindings** — rejected: the bindings are marked
  "Do not edit this file manually," and the Rust back-end is not in this repo, so a
  `#[ts(type = "number")]` override would couple this front-end change to cross-repo
  regeneration. The barrel transform keeps the generated files pristine and the fix
  self-contained.
- **Preserving `bigint` end-to-end** (a custom i64-safe JSON parse) — rejected: JSON
  already collapses ids to `number` before any code runs, so the `bigint` types were
  cosmetic; a custom parser would be a large change fighting the wire format.

## Consequences

- Ids above `Number.MAX_SAFE_INTEGER` (2⁵³−1) lose precision. This was already true
  at runtime; we now make the type honest about it rather than implying an i64 safety
  the code never delivered. Acceptable for a demo; revisit if the back-end ever issues
  ids beyond that range.
- `serializeWithBigInt` is removed: with no `bigint` values in play, request bodies
  serialize with plain `JSON.stringify`.
