Problem

Solution

  • leverage: each new form inherits six rules
  • one test suite at the interface
  • useDraft folds into the module

Problem

The view-model lists scopes by hand: 5 for the Post, 2 for a Caption pick, 1 for a Caption delete. postScopes is set late, a new ordering trap. A form gets its scope through optional props. A missed prop puts its Draft in no scope, and every scoped move skips it.

Solution

Each scope nests under its subject: the Post, then the Caption. A move names one subject, and the guard finds every Draft under it. A form takes its scope from where it mounts.

Wins

  • no hand-kept scope lists
  • no late-set postScopes
  • a missed scope cannot occur
  • 26 fake form reports simplify

Leak: the Caption delete releases 1 scope. That is safe only because FeaturedPost disables Delete while the Caption edit is open.

Problem

A Caption add runs in the form, through its own api seam, and waits for the poke. A Caption edit runs in the view-model and refetches at once. The Post splits the same way.

Solution

The view-model, or the C-25 module, owns every write on a subject. Each form gets one write function.

Wins

  • locality: one refetch rule per subject
  • one seam to the back-end
  • forms stop injecting api slices

The two rules behave differently today. The maintainer decides which rule is correct before any move.
