Small interface, large behaviour behind it. The interface is now the test surface.

Problem

The merge/dedupe/stale-guard logic — where the real bugs live — has no locality: it is spread across three effects, a mutable listStale flag, and two copies of the dedupe check.

Solution

Move the live-stream protocol behind one module, createConvMessages(conv), exposing messages / send / connected / error; the WebSocket and RPC become internal seams.

The bug-prone logic, quoted — dedupe written twice 

// MessagePanel.tsx:26  (inside onConvMsg)
if (prev.some((m) => Number(m.id) === Number(msg.id))) { return prev; }

// MessagePanel.tsx:86  (inside handleSend)
setMessages((prev) => prev.some((m) => Number(m.id) === Number(msg.id)) ? prev : [...prev, msg]);

// MessagePanel.tsx:16  — mutable race-guard, untestable except through the DOM
let listStale = false;

Wins

  • ▸ locality: dedupe + stale-guard in one place
  • ▸ interface becomes the test surface
  • ▸ tests stop mocking two seams to reach merge logic
  • ▸ leverage: one stream module, reusable per conversation
Deletion test: delete the module and the subscribe / list / dedupe / stale choreography reappears in every place that shows a live conversation. It concentrates complexity — it earns its keep.

createRpcAction(fn)

{ run, pending, error }

reset error → pending true → try → catch → finally
tested in isolation, no DOM

Each caller keeps only its bespoke success step (refetch, onSelect).

Problem

The reset-error / set-pending / try / catch / finally choreography is copied verbatim into three submit handlers; only the success step differs.

Solution

A small createRpcAction(fn) module owning run / pending / error; callers pass the RPC and their own success step.

The repeated shape, quoted

// AgentManager.tsx:16 / ConversationManager.tsx:39 / MessagePanel.tsx:73 — same five moves
setError(null);
setCreating(true);          // setSending(true) in MessagePanel
try { const x = await backendRpc.…; form.reset(); /* bespoke success */ }
catch (e) { setError(e instanceof Error ? e.message : "Failed …"); }
finally { setCreating(false); }

Wins

  • ▸ locality: pending/error policy fixed once
  • ▸ leverage: one module, three call sites
  • ▸ module testable without rendering a form
  • ▸ callers shrink to their real difference
Honest caveat: the three handlers diverge in their success step (one refetchs, one fires onConvSelect, one sets a stale flag). The module must capture only the shared state machine and leave the success step to the caller — otherwise it adds shape without adding depth. Grill this before committing.

Problem

Generated types declare id: bigint, but response.json() yields number — so every caller sprinkles Number(id) to paper over a divergence the seam never resolved.

Solution

Make the RPC adapter the single seam that normalizes identity (decide on number or a branded Id); downstream compares ids directly.

Type vs runtime, quoted

// types/backend/Agent.d.ts:4  — generated, declares bigint
id: bigint;

// lib/backend-rpc.ts:46  — JSON.parse yields number, not bigint
const json: JsonRpcResponse<T> = await response.json();

// lib/backend-rpc.ts:87  — defensive coercion, one of ~10
get: (id) => rpcCall<Agent>("get_agent", { id: Number(id) }),

Wins

  • ▸ locality: identity duality lives at one seam
  • ▸ types match runtime — fewer silent lies
  • ▸ dedupe/compare logic drops the Number() tax
  • ▸ leverage: one decision, every call site benefits
Constraint: the .d.ts files are generated by ts-rs — “Do not edit this file manually.” The fix belongs at the adapter (parse/normalize on the way in), or in a ts-rs override, not by hand-editing the bindings. That constraint is the whole reason this is Worth exploring, not Strong.

Top recommendation

01 · Collapse the live Message stream

It is the one place where the bug-prone logic — dedupe, stale-guard, subscribe lifecycle — has no locality and no honest test surface: today the merge logic is reachable only by mocking two seams and driving the DOM. Deepening it into createConvMessages(conv) gives the largest gain in both leverage and locality, and it passes the deletion test cleanly. Candidates 02 and 03 are real but each carries a caveat worth grilling first.
