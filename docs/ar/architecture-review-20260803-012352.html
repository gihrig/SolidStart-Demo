Worth exploring in-process Jedi

Before — one claimed boundary, answered 0, 1, and 2 times

data.json safe() @ jedi-api → no gate → render src={p.author.avatarUrl} ×1 — sidebar, JediNav

After data.json sanitize seam @ jedi-api — the one gate → every consumer binds trusted output 
// jedi-api.ts:19 — the intended single boundary (asserted by its unit test)
const safe = (url) => sanitizeUrl(url) ?? "";   // every URL field routes through it
// Author.tsx:12 re-sanitizes:  const imgSrc = () => sanitizeUrl(props.avatarSrc);
// TopPhotosCard.tsx:50 trusts it raw:  <img src={p.author.avatarUrl} />

Problem. jedi-api sanitizes every URL, yet Author/Image/Hero sanitize again while the sidebar cards and JediNav bind raw — the "single boundary" is answered three ways.

Solution. Make the jedi-api seam the sole owner; consumers bind its trusted output; drop the leaf-level re-sanitizing.

Wins

  • one seam answers "is this URL safe"
  • delete redundant leaf sanitizing
  • close the sidebar's sanitize gap
  • locality: policy fixed in one place
Supports ADR-0002. The ADR already names the jedi-api seam as "the single trust boundary where every URL field passes through sanitizeUrl." This deepening honors it — the friction is that the code doesn't. Grill: are Author/Image meant to be defensive reusable primitives (defense-in-depth) beyond Jedi? That's the one real counter-argument.

return { connected, error, subscribe, unsubscribe, disconnect, reconnect: connect };
// error() is redundant with the onError callback; disconnect/reconnect: zero production callers

Problem. useWebSocket returns six members (three unused in production) behind two near-identical option types — interface width without matching leverage.

Solution. Return the MessageFeed port callers actually use; keep reconnect/disconnect as private implementation; collapse to one options type.

Wins

  • interface shrinks to 3 real members
  • delete dead disconnect/reconnect/error
  • one options type, not two
  • test drives the port, not internals
Why Speculative: reconnect is partly there so the unit test can trigger connect (onMount doesn't fire in the harness). Trimming the surface means solving that test seam first — hard-to-test leaking into a wider interface.

Top recommendation

Start with #1 — unify the async-mutation choreography.

It has the most leverage: one deep RpcAction concept is hand-rolled at four call sites, and the payoff is a concrete behaviour change, not a rename — MessagePanel deletes its own sending signal and the send lifecycle (pending + error) becomes testable through createConvMessages's interface instead of only through the DOM. That directly closes the untested wiring gap in the Conversations slice.

If you want a smaller, self-contained first cut instead, #2 (sidebar selection has two owners) is the cleanest quick win — deleting a genuine second source of truth for the #37 highlight.
