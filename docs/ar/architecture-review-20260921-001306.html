Architecture review — lib-core

2026-09-21 · issue #165 · continues C-09

Deepening pass on backend/crates/libs/lib-core (the domain / model / store crate). The mechanical mod.rs pass (#161) already landed. lib-core is a faithful rust10x model layer — deeply layered already: the generic base CRUD sits behind DbBmc, the store is private, and each entity BMC hides real work (the PostView assembly is a deep module). So these candidates target internal locality and interface curation, not a shallow public seam. The one large shallowness — Postgres welded through every layer — is already owned by ADR-0012 and deferred (see C-12).

Problem

The tables post_like / post_comment / post_category are named as string literals in four spots, and PostCategoryBmc — the typed owner that already exists — is bypassed with Alias::new("post_category").

Solution

Add PostLikeBmc / PostCommentBmc marker BMCs (like PostCategoryBmc), make counts_by_post take MC: DbBmc, and route every read through MC::table_ref().

Wins
  • locality: each table name lives in one BMC
  • the like / comment write path (#118, #122) reuses the seam
  • the compiler, not a string, checks the table
  • kills the defined-but-bypassed PostCategoryBmc
Deletion test: weak leverage today — the counts feed one caller (assemble_views). The win is locality now, and a real seam once post_like / post_comment gain a write path (#118, #122). The tell that it is not speculative: post.rs:585 already notes “post_like has no Bmc yet (#118)”, and PostCategoryBmc is defined at post.rs:128 yet bypassed at post.rs:528.

Problem

model/mod.rs:33 declares pub mod modql_utils;, but its only item, time_to_sea_value, is a sea-query decode helper used only inside the crate. No consumer imports it.

Solution

Tighten modql_utils to pub(crate). The entity files keep their use crate::model::modql_utils::time_to_sea_value; unchanged.

Wins
  • interface shrinks; implementation keeps the helper
  • serves #165’s “curated public API” criterion
  • the seam reads as: ModelManager, Ctx, BMCs
  • low risk: an in-crate use path, not the export surface
Adjacent (note, not this pass): model/mod.rs:32 also exposes pub mod conv_user;, whose ConvUserBmc is unimplemented scaffolding (conv_user.rs:51) that the Jedi merge drops (#106, every Post public). Retiring it belongs to the merge, not this curation pass.
Candidate C-12

The store is welded to Postgres — but ADR-0012 owns it

⏸ Deferred ports & adapters
model/store/pool.rs · model/store/dbx/executor.rs
model/base/crud_fns.rs · every model/*.rs (FromRow<PgRow>)
Cross-section — one driver threaded through every layer
model/*.rs decode E: for<'r> FromRow<'r, PgRow>
base/crud_fns.rs build_sqlx(PostgresQueryBuilder)
store/dbx/executor.rs QueryAs<'q, Postgres, …> · Transaction<'static, Postgres>
store/pool.rs pub type Db = Pool<Postgres>

The interface (DbBmc, ModelManager) is small, but the implementation names one concrete driver at every band — a real, wide shallowness. A second backend has no seam to enter.

Why it is deferred, not proposed

ADR-0012 already maps this exact coupling and calls it “total, not one module”. It picks a cfg-selected backend module at compile time, and explicitly rejects the runtime trait / sqlx::Any shape.

Scope

ADR-0012 breaks this out into “its own back-end-expansion track”, separate from the Jedi merge. It is not part of the #165 clean-architecture pass, and a runtime-trait version would fight the decision (as C-08 / C-09 fought the blueprint).

⚠ Contradicts nothing worth reopening. This card exists so a future review sees the coupling was observed and is owned by ADR-0012 (2026-09-19). Do not re-suggest a store trait here — take it on the Turso track, per the ADR.
