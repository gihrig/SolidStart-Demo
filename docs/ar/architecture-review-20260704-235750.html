SolidStart-Demo — the icon system after issue #11

2026-07-04 · branch #11-png-icons-sprite · scope: the sprite migration touched system-icons.ts, jedi.tsx, JediNav.tsx, icon-sprite.svg.

module seam duplication / leak deep module

The migration is sound, but it left four parallel ways to render one sprite icon. Understanding "how do I show an icon here" now means bouncing between four modules. Every candidate below is about restoring locality to the icon system and deepening one interface over it.

1 · Deepen icons into a single <Icon> module

Strong in-process
src/lib/system-icons.ts · src/routes/jedi.tsx · src/components/JediNav.tsx · src/components/ThemeToggle.tsx · src/icon-sprite.svg

Four routes to the same sprite. The red one doesn't even reach it — it re-draws symbols the sprite already holds.

After — one deep module

interface

<Icon name="fire-heart" />

implementation (hidden)

svg + use + #icon- prefix

IconName union derived from sprite

class passthrough

Narrow interface, everything else absorbed. Every call site names an icon and nothing else.

Registry today — interface ≈ implementation (shallow)

interface: 5 exports
impl: lookup + map + 2 throwers

getSystemIconIcon & SYSTEM_ICON_MAP are dead — used only by each other.

<Icon> — short interface, deep impl

interface: name
impl: svg/use/prefix/types

Callers stop knowing about #icon- prefixes and <use> markup.

Problem
Rendering an icon means picking one of four mechanisms; the sprite has no single module that owns "which icons exist."

Solution
One <Icon name /> component owns the <svg><use> markup and the #icon- prefix; name is a union derived from the sprite ids.

Wins

  • leverage: one interface, 7+ call sites
  • locality: icon bugs land in one module
  • typos caught at compile time, not blank render
  • delete the whole shallow registry
  • the interface is the test surface — one test

Evidence — the boilerplate repeats, the registry half-serves its callers

ThemeToggle <use>s the sprite (or the <Icon> of candidate 1). Symbols stop being dead.

Problem
The sun/moon/system glyphs live in two places; the sprite copies are dead weight and can silently drift from the inline ones.

Solution
Pick one home. Either ThemeToggle <use>s the sprite symbols, or drop them from the sprite. Candidate 1 makes the first choice free.

Wins

  • locality: one definition per glyph
  • no drift between sprite and inline copy
  • sprite becomes the single source of truth

3 · Avatar URLs are scattered stand-in data

Speculative data, not module
src/routes/jedi.tsx · src/components/JediNav.tsx
Aligns with CONTEXT.md, not against it. The Jedi glossary is deliberately deferred until the content is database-backed. These literals are placeholder data, not a shallow module — so the honest recommendation is leave it until the User/avatar model lands. Listed only so a future explorer doesn't mistake the scattering for an oversight.

Observation
Six img.icons8.com/doodle/… avatar URLs repeat across TOP_PHOTOS, TOP_CAPTIONS, the Author avatar, and JediNav's Bart avatar.

Why defer
Extracting an avatar seam now would model a User that CONTEXT.md says isn't pinned yet — premature modularization. The real seam arrives with the DB-backed model.

If revisited later

  • avatar belongs to the future User/author model
  • one seam when the data is real
  • not a two-adapter situation yet

Evidence — same URL literal, four call sites

Top recommendation

Start with candidate 1 — the <Icon> module.

It has the strongest deletion test: an <Icon name /> component absorbs the <svg><use> boilerplate and the #icon- prefix, lets the sprite ids become a compile-checked union, and lets the entire shallow system-icons.ts registry — including its two dead exports — be deleted. Candidate 2 then falls out for free, because ThemeToggle simply names its icons.
