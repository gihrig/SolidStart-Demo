Architecture review

SolidStart Demo · backend/ · 2026-08-18 · branch arch-review-8-18

First architecture review of the Rust/Axum back-end — the previous seven all looked at frontend/. The rust10x spine is well-shaped: crud_fns is a deep generic base, Dbx hides transaction ref-counting behind a tiny interface, and two macros (generate_common_bmc_fns! / generate_common_rpc_fns!) keep the entity boilerplate thin. All three friction points below share one spine: the server threads a Ctx — the caller's identity and scope — through every layer, then never acts on it. Reads, deletes, and the realtime fan-out all ignore who is asking.

The connection to the front-end review

The front-end's landed C1 fixed a conv.list filter double-wrap that had "leaked every Agent's Convs." That was the symptom. This review finds the root: the back-end never scoped the query by Owner in the first place, so a broken — or absent — client filter silently widens the result set instead of being rejected.

01 Strong authorization seam Landed

Give the ownership invariant a home at the read seam

model/base/crud_fns.rs · model/base/mod.rs · model/base/utils.rs · lib-rpc-core/utils/macro_utils.rs

CONTEXT.md is explicit: a Conversation is "owned by the Standard user who created it," and "only its Owner or an Admin user may delete Messages or the whole thread." The back-end writes owner_id on create and then never reads it back. The Ctx — passed to every CRUD function — is used only to stamp audit columns.

Status — C01 slice landed

A per-Bmc access_scope(ctx, Access) hook on DbBmc (default None) now scopes all six ctx-taking base CRUD functions: read-scope (owner ∪ public) on get/list/count and write-scope (owner-only) on update/delete/delete_many. A wrong Owner is indistinguishable from a missing row — EntityNotFound, assertable at the Bmc — with the root context (user_id = 0) bypassing scope once in base. Recorded in ADR-0014; design in c01-owner-scope-design.md.

  • → Conv: read owner_id = me OR kind = 'MultiUsers', write owner_id = me. ConvMsg reads scope via a parent-conv subquery; Agent reads for all Users, writes creator-only.
  • → Deliberately narrower than the privilege ACS: the Admin typ = Sys delete override, add_msg post-permission (the next slice), and Member reads are documented, deferred gaps — not silent ones.
  • → Resolved candidate 02 as a side effect: the dead ConvScoped / Ctx.conv_id scaffolding is retired (no live caller). Verified by a non-root two-user Bmc matrix plus one cross-user HTTP case.

Problem

get / list / delete accept a _ctx they discard. has_owner_id() is declared true on Agent and Conv but only fires at create. So get_conv(id) returns any User's Conversation by guessed id, and the Owner-scoping the front-end sends is a courtesy, not a guarantee.

Solution

Make the read seam consult has_owner_id() the way create already does: when an entity has an Owner, add owner_id = ctx.user_id() to the WHERE inside base::{get,list,delete}. The invariant moves out of client filters and into one module.

Wins
  • ▸ locality: the Owner boundary lives in one seam, not N callers
  • ▸ leverage: every Owner-scoped entity gets it free
  • ▸ the interface stops taking a _ctx it ignores
  • ▸ test surface: "wrong Owner → EntityNotFound" becomes assertable at the Bmc
Open design questions (for grilling): root_ctx() carries user_id = 0 — the scope must exempt Admin / system callers, and Members (not just Owners) must still reach a MultiUsers Conversation. This is the minimal owner-scope slice — deliberately narrower than the rust10x privilege ACS the blueprint defers (candidate 02), not a replacement for it.
02 Worth exploring hypothetical seam · 0 adapters

Decide the fate of the inert ACS scaffolding

ctx/mod.rs · model/conv.rs · model/conv_msg.rs

A future Access Control System is scaffolded across three files — ConvScoped (a trait, implemented three times), Ctx.conv_id with add_conv_id() and a conv_id() accessor, and a TODO in get_msg. Grep says the trait method and the Ctx field are never called outside a comment. Apply the deletion test and it all vanishes cleanly: today it is a seam with zero adapters — exactly what the design vocabulary says not to build until something varies across it.

Problem

Three files carry the vocabulary of an access-control seam that no code path exercises. A reader (human or agent) can't tell scaffolding-for-later from a live-but-buggy check — the intent reads as implemented.

Solution

Tie it to candidate 01. If 01's owner-scope needs Message→Conversation resolution, get_msg is the first real adapter and the scaffolding earns its place. If not, retire it and let the future ACS reintroduce it deliberately.

Wins
  • ▸ "one adapter = real, zero = hypothetical" — resolved either way
  • ▸ the code stops describing behavior it doesn't have
  • ▸ AI-navigability: no phantom seam to reason around

Held at "worth exploring": this is intentional rust10x forward-scaffolding, so the call is a judgement about honesty-of-interface, not a bug. Its answer falls out of candidate 01.

03 Worth exploring inverted module

The WebSocket channel that nothing routes on

src/web/routes_ws.rs

The realtime feed is an inverted module: its interface is more sophisticated than its behavior. Clients send a SubscriptionRequest {action, channel, id}; every broadcast is stamped with a channel like conv:42. But the subscription handler is a no-op and the channel is never matched — every connected client receives every event. Two of the three broadcast helpers have zero callers.

Problem

The interface promises per-channel subscription; the implementation ignores it and fans out everything. Callers must learn a protocol that does nothing, and the channel field reads as meaningful when it is inert.

Solution

Deepen or shrink. Deepen: hold a subscription set per connection and filter by event.channel in the send task — the channel becomes real, and it aligns the push path with candidate 01's Owner boundary. Shrink: drop the subscription protocol and the channel field until a second consumer needs it.

Wins
  • ▸ interface stops over-promising
  • ▸ private Conversations stop leaking on the socket
  • ▸ removes 2 dead helpers, or gives them a caller

Larger than 01: "deepen" needs per-connection state and touches the front-end's #85 live-propagation work. Worth exploring after the contained Bmc win lands.

Tackle first

01 · Give the ownership invariant a home at the read seam

Smallest change with the widest reach: one predicate in base::{get,list,delete}, gated on the has_owner_id() that already exists, and every Owner-scoped entity inherits it. It is the server-side root of the front-end's just-landed C1 filter leak — fixing it turns the client's Owner filter from a courtesy into a guarantee. It also decides candidate 02: if the scope needs Message→Conversation resolution, the inert ConvScoped / Ctx.conv_id scaffolding becomes its first real adapter. Candidate 03 is the same boundary on the realtime push path — worth exploring once the contained Bmc win is in.
