Architecture review — lib-web

2026-09-21 · issue #166 · continues C-12

Deepening pass on backend/crates/libs/lib-web (the presentation crate: Axum handlers, middleware, the web Error). The mechanical mod.rs pass (#162) already landed — every mod.rs is wiring-only. The crate is a faithful rust10x web layer and small (896 lines): the RPC handlers already delegate to one rpc_dispatch, and error.rs is a genuinely deep module (small interface, dense mapping). So the friction is narrow: an over-wide public interface, one handler that is not thin (and matches the blueprint), and an error seam that maps RPC-wrapped model errors twice — with a gap.

Problem

lib.rs:6 and lib.rs:9 export pub mod log and pub mod utils, but no crate outside lib-web imports either. utils/token.rs:1-2 also re-exports Error / Result / ClientError, so the web Error is reachable by two paths.

Solution

Make log and utils pub(crate) (their callers are all in-crate). Drop the Error / Result / ClientError re-exports in token.rs; keep the one use crate::error::Result it needs.

Wins
  • interface shrinks; implementation unchanged (deeper)
  • serves #166's "curated public API" criterion
  • one public path to Error
  • low risk: visibility only, no caller changes
Deletion test: removing pub from log / utils deletes zero external callers — a grep for lib_web::log / lib_web::utils across crates/services is empty. Pure surface reduction. This mirrors C-11, shipped for lib-core the same way.

Problem

api_login_handler (handlers_login.rs:15-66) mixes Axum extraction with the login flow — user lookup, validate_pwd, scheme upgrade, cookie. The flow has no interface but the HTTP handler.

Solution

Extract a login function taking the model and credentials; the handler parses the payload, calls it, sets the cookie, and shapes the body — thin and delegating.

Wins
  • the scheme-upgrade branch testable directly
  • handler becomes thin (the #166 ask)
  • locality: the login flow lives in one module
  • the interface is the test surface, not HTTP
⚠ Diverges from the rust10x blueprint. The blueprint keeps this exact flow inside api_login_handler. C-08 / C-09 were rejected in favor of the blueprint (commit 4a613da), so this may go the same way. Surfaced because #166 asks for "thin handlers that delegate"; the RPC handlers already are (they delegate to rpc_dispatch), so login is the one exception — and it matches the blueprint.
Deletion test: weak leverage — one caller. The flow is not a pass-through, so extracting concentrates the login logic where its bugs live (pwd match, scheme upgrade) rather than moving it. The gain is test locality, not a second adapter — hence Speculative. An in-process HTTP test already covers login end-to-end (web-server/src/app.rs).
Candidate C-15

Flatten RPC-wrapped model errors so the client map matches once

✓ Shipped Strong in-process locality
error.rs (From<CallError> · client_status_and_error)
✓ Shipped in #166. From<CallError> now flattens the handler's lib_rpc_core::Error into Error::Model / Error::SerdeJson; the RpcLibRpc variant and the dead Rpc variant are deleted; the client map has one Model(..) arm per kind. An RPC "entity not found" is now 400, not 500 (#114). New test rpc_wrapped_model_error_flattens_to_400 drives the real From<CallError> path. Bindings regenerated (both variants leave lib_web_Error.d.ts; FE unaffected); docs/error.md updated. Gate green: check · build · test (99/99) · bindings.

Problem

client_status_and_error maps model errors twice. Validation has a direct arm and an RpcLibRpc(Model(..)) arm (error.rs:172-185). EntityNotFound has only the direct arm (error.rs:168-171), so an RPC read of a missing entity falls to the _ => fallback (error.rs:221-224) → HTTP 500.

Solution

At the From<rpc_router::CallError> deconstruction (error.rs:96-101), flatten the known lib_rpc_core::Error::Model / SerdeJson into lib-web's own Model / SerdeJson. Then the client map matches each model error once.

Wins
  • fixes EntityNotFound-via-RPC 500 → 400
  • locality: one arm per model error kind
  • leverage: new model errors map once, not twice
  • deletes the RpcLibRpc pass-through variant
Deletion test: delete RpcLibRpc (error.rs:55). Its construction at error.rs:100 unwraps into Model / SerdeJson, and the wrapped Validation arm collapses into the direct one — complexity concentrates in From, not spread across the match. This finishes the #114 fix (the double-arm was added to stop the same 500), rather than re-litigating it.
Consider during grilling: flattening makes the log's error_type read Model for the RPC path instead of RpcLibRpc. The RpcInfo method / id are logged separately, and RpcRouter / RpcHandlerErrorUnhandled still catch the other rpc-router cases.
