01 Strong ports & adapters

Deepen the backend-rpc list interface

Before — filter language leaks, inconsistently

Three list methods, three filter conventions. The real filtered call and its test never agree on the shape.

After — one owner of ModQL, domain args only
caller
conv.list({agentId})
ModQL — internal
[{agent_id:{$eq}}]
caller
convMsg.list(convId)
[{conv_id:{$eq}}]
the ModQL dialect lives here — and only here
Callers pass domain ids. The {$eq} shape, and its one wrapping, are the module's private business. The test exercises the shape callers actually send.
backend-rpc.ts:85–104 
// agent + conv: raw passthrough
list: (filters?: Record<…>) =>
  rpcCall("list_convs", { filters }),
// convMsg: owns the ModQL
list: (convId: number) =>
  rpcCall("list_conv_msgs", {
    filters: [{ conv_id: { $eq: convId }}]
  }),
conversationWorkspace.ts:70 — the real call 
await backendRpc.conv.list({
  filters: [{ agent_id:
    { $eq: agent.id } }],
})
// arg → params.filters =
//   { filters: [ … ] }  ← wrap²
backend-rpc.unit.test.ts:288–292 
await conv.list({ agent_id: 1 });
expect(body.params).toEqual({
  filters: { agent_id: 1 }
});
// asserts a shape the real
// caller never sends
Problem

The ModQL filter dialect leaks across the seam, and each list method leaks it differently — so the one real filtered caller double-wraps it and the unit test asserts a third, unused shape.

Solution

Give every list method a domain-shaped interface (conv.list({ agentId })) and build the ModQL inside — the way convMsg.list already does.

Wins
  • ▸ locality: ModQL dialect lives in one module
  • ▸ interface shrinks; implementation absorbs the shape
  • ▸ test surface matches the real call
  • ▸ resolves a likely latent filter bug
Verify first: whether the double-wrapped filters is silently dropped server-side — if so, conv.list returns every agent's Conversations. The e2e (fullstack.spec.ts) creates only one Agent, so it can't surface this; the client-side resource re-key masks it in the demo.

the RPC half — a module mock, not a seam 
// createConvMessages.ts:60,81 — singleton
backendRpc.convMsg.list(c.id)

// its test:8 — mock the whole module

The seam material already exists: createRpcClient() is a factory (backend-rpc.ts:49) whose own tests spin up fresh clients — it just isn't threaded into the view-models, which reach for the backendRpc singleton instead. The MessageFeed port shows the target shape; the RPC side should match.

Problem

Every view-model binds a module singleton, so the only way to test past the interface is vi.mock — the test crosses through the module instead of standing at its seam.

Solution

Accept an injected client (like feed), default it to the real one. Tests pass an in-memory adapter — the same discipline the socket port already earns.

Wins
  • ▸ the interface becomes the test surface
  • ▸ two adapters justify the seam: real + in-memory
  • ▸ drops vi.mock from createConvMessages' test (the workspace's follows in #85, jedi's in #67)
  • ▸ one consistent injection story, socket + RPC
03 Worth exploring in-process

Collapse the three hand-spelled CRUD blocks into one crud(entity)

src/lib/backend-rpc.ts · src/types/backend/index.ts

Before — envelope re-spelled per entity
agent
create {data}
get {id}
list {…}
update {id,data}
delete {id}
conv
create {data}
get {id}
list {…}
update {id,data}
delete {id}
convMsg
add {data}
list {…}

Twelve method-name strings and the {data}/{id}/{id,data} shapes hand-repeated — the same shapes the ParamsIded / ParamsForUpdate bindings already name. Interface surface ≈ implementation: shallow.

After — one factory owns the envelope
crud<E>(name)
create · get · list · update · delete
▼ instantiated three times
crud("agent")
crud("conv")
+ convMsg

Envelope shapes defined once, typed against the shared Params* bindings. Interface shrinks to three lines; implementation absorbs the repetition.

a second, differently-shaped door: auth sits outside the factory 
// backend-rpc.ts:20 — module singleton, not in createRpcClient()
export const auth = { login, logoff };
// login returns { result:{ success } } — AuthContext.tsx:52
// ignores it entirely (throws-or-ok). Shallow return, no reader.
Problem

Three near-identical CRUD blocks re-spell the RPC envelope twelve times; auth is a fourth, different door in the same module with a return no caller reads.

Solution

A crud(name) factory owns {data}/{id}/{id,data} once, typed against the Params* bindings; fold auth into the same client.

Wins
  • ▸ leverage: one envelope, N entities
  • ▸ deletes ~10 shallow method wrappers
  • ▸ envelope typed once against bindings
  • ▸ pairs naturally with candidate 01

Rides on the same module as 01 — do them in one pass. Held at "worth exploring" because the repetition is dull, not dangerous: no correctness risk, just surface area.

Tackle first

01 · Deepen the backend-rpc list interface

Smallest blast radius, highest confidence, and the only candidate touching a likely correctness defect: the filter dialect leaks, the one real caller double-wraps it, and neither the unit test nor the e2e can catch a broken Agent filter. Fixing it concentrates the ModQL dialect in one module and makes the test surface match the real call — then candidate 03 rides along in the same file. Candidate 02 is the larger structural follow-up — worth it, but it changes every view-model's interface, so land the contained wins first.

Vocabulary: module · interface · depth · seam · adapter · leverage · locality — /codebase-design. No ADR conflicts: candidates 02–03 complement ADR-0005 (RpcAction) and ADR-0010 (ts-rs bindings).
